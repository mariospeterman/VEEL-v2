3. LOCAL FIXES STILL REQUIRED

F01 — P1: 0130 cannot upgrade an ordinary populated preference table.
packages/database/migrations/0130_media_core_scope_transition.sql:4 updates recommended to latest before removing the existing CHECK at:11. The old CHECK allows recommended/following only. An existing recommended row causes SQLSTATE 23514, aborting the migration. A disposable probe applied the actual chain through 0129, inserted that valid historical state and reproduced the failure. An empty-table CI migration can pass while this upgrade fails. Fix through the reviewed immutable-migration/bridge procedure; do not change a migration silently if a retained/shared environment or durable migration history already applied it. A migration after 0130 alone cannot repair an earlier failure in the chain. Require a populated 129→current native PostgreSQL regression.

F02 — P1:canonical identity/session/recovery access is still overbroad for low-privilege staff.
New 0132 correctly revokes the finance surfaces it names, but does not repair the canonical identity/session/recovery tables from DB-01. With the actual 132 schema and explicit repository grants, a linked authenticated event_ops identity can read another user's user_provider_identities, app_sessions metadata/token hashes and recovery_link_intents metadata/token hashes. These are token hashes, not plaintext credentials; no account-takeover claim is made. Read the full migrated grant/policy catalog, preserve legitimate self-service/Realtime and enforce action-specific staff permission or remove direct access. Prove both explicit-grant and retained-grant histories with native roles.

F03 — P1:current verification still has conflicting authorities.
The age repository chooses the current event, but profile-dashboard-repository.ts:350,368 and effective private.resolve_creator_kyc_state in 0108 still prefer historical valid evidence. Organization and managed-creator KYB readers retain the same pattern. Current-head probes produce canonical age blocked while onboarding says age_verified=true; an actual migrated earning-policy function returns verified for older valid KYC followed by newer blocked KYC. This proves contradictory projections and policy selection, not that every separate HTTP guard is bypassed. Share one subject/purpose current-decision selector across runtime SQL and application consumers, then evaluate assurance/expiry/revocation.

F04 — P1 functional blocker:adult approval cannot supply its required performer age fact.
verification-repository.ts:523 writes threshold_age/result_over_threshold only for age_access. Approved adult_publisher_eligibility gets NULL, while content-safety-repository.ts:123 and performer-repository.ts:287 require result_over_threshold on that adult record. The derived age record does not meet that predicate. The exact writer/selector probe returns zero eligible evidence rows. Persist authenticated purpose-specific adult facts or deliberately link acceptable adult+age evidence through one policy; do not infer adulthood from document/liveness success. Prove the native provider-normalization→performer→release→publish path.

F05 — P1/P2:lost age/ID responses still cannot resume the same attempt.
Reservations reject an identical key instead of returning a durable resumable launch handoff. No authenticated attempt-resume path is present. A new click uses a new key and may create another remote session while the first is pending. The no-automatic-second-provider safeguard is good but does not complete recovery. Implement durable attempt status/resume/reconciliation using the selected provider's supported API. Long document processing must remain recoverable, not depend on a short landing poll loop. Yoti retry/resume flags are now requested, but same-signed-second fail→pass ambiguity still needs authenticated result reconciliation; do not trust unsigned sequence numbers. Parsed reverify settings are also not runtime policy implementation.

F06 — P1 money risk:wallet retry can ask the user to make a second transfer.
apps/web/src/payment-wallet-bridge.tsx:44 obtains a broadcast signature;:45 can fail while acknowledging it to WeVid. The catch path loses the signature, and Try connected wallet again clears the guard and rebuilds/signs another transaction. The backend can rebuild a submitted intent, so it does not prevent a second debit when a refreshed blockhash is used. A bounded execution of the exact async source with mocked wallet/API demonstrates two distinct signatures for one intent after first-acknowledgement loss. No chain transfer was sent. Retain and reconcile the first signature/logical command before requesting wallet approval again; distinguish pre-sign rejection from post-send uncertainty. Backend duplicate receipt protection alone cannot undo a second direct transfer.

F07 — P1/P2:feed restoration can replace fresh safety preferences with stale resources.
feed-experience.tsx:235 restores a full cached page for up to 30 minutes over freshly authorized server data. Cache key: clientSessionScope+surface+mode, without sensitivity/policy generation. Both→Safe-only in Settings followed by Home can restore old adult cards; hide/block/unpublish changes can also be lost on return. Preserve scroll geometry/IDs, invalidate relevant policy state and reauthorize/hydrate restored visible items before showing resources. This is a static state-flow finding, not a live browser bypass reproduction.

F08 — P1/P2:historical poll replay reads current private projection without authorization.
content-poll-repository.ts:25 calls selectPoll for an old completed key;:35 reads current question/options/counts without current visibility/eligibility/block checks. The receipt only retained reference IDs, not an immutable saved response. A former voter can therefore use their old receipt to read the current projection after unpublish/private/block changes. The route checks app readiness, not that content's access. Reauthorize current reads or return only an appropriate immutable historical receipt; keep all new voting disabled. Do not solve this by reopening polls or deleting historical votes.

F09 — P1/P2 reliability:paid/member/owner video resources have no expiry renewal path.
ProviderPlayback expires every playback resource but offers renewal only if playback.usage exists. Owner, paid/member and other non-allowance resources may legitimately omit usage. Their supplied ContentRenderer callback is unreachable, and the proactive timer covers images only. Live viewer playback supplies no refresh callback. Long video/live sessions can become placeholders until reload at token expiry. Separate capability renewal from public-allowance reservation, retain current authorization and use bounded keyed refresh without duplicate usage/payment effects. This is source-traced, not actual provider playback proof.

F10 — P2:camera capture lacks a current application-session revocation boundary.
The host component clears credentials/tracks on explicit stop/unmount or manually refreshed room state. It has no cross-tab logout/account-switch listener or periodic current-owner/session reconciliation after exposing the direct provider capability. Add browser session-change cleanup and the selected provider's supported ingest revocation/rotation/expiry policy. Explicitly distinguish app cleanup from provider enforcement and advanced OBS behavior. Actual continued provider broadcast after logout/revocation was not tested or claimed.

F11 — P2/performance:chronological ordering is not yet bounded eligibility work.

The UI bounds rendered cards but retains accumulated page metadata/heights/cache; do not confuse a DOM bound with a measured total-memory bound.
