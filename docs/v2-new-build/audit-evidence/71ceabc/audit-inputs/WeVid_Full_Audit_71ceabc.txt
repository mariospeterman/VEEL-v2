4. CREATOR OWNERSHIP, PERFORMANCE AND PROVIDER FIT

Recommendation: preserve managed media delivery and add strong rights/portability controls. A creator should retain legal rights under approved terms, choose visibility, export retained originals plus a versioned metadata manifest with one action, and retire/delete content under the accepted paid-access/retention policy. Ordinary creators should not set up provider APIs or storage accounts. Keep media and likes off the transaction path; Solana handles direct payments and optionally a narrowly described signed manifest.

| Option | User effort / performance | Actual ownership and deletion boundary | Decision |
|---|---|---|---|
| Managed Bunny media + async export + explicit rights | Normal upload/playback; bounded background export; no creator API setup | Creator rights/portability, while WeVid controls provider account; configurable purge subject to holds and existing tokens/copies | Recommended default |
| One-click delegated creator provider account | Potentially simple only if provider has documented delegation/transfer | Stronger operational independence if contract/API actually grants it | No verified Bunny OAuth/transfer flow; do not invent one |
| Wallet-signed export manifest | Optional single signature, outside feed latency | Attests wallet assertion/hash relationship; not copyright, consent or guaranteed possession | Optional later, without sensitive public metadata |
| Public immutable/distributed media default | Adds infrastructure and may add another chain; key/recovery/cache complexity | Independent copies cannot be recalled; conflicts with revocation/privacy/removal | Poor default for this product |

Bunny's /original resource requires Keep original files enabled; verify current and historical retention before promising an original-file export. KeepOriginalFiles (retention) is distinct from ExposeOriginals/AllowEarlyPlay (CDN exposure); exposed originals are not DRM protected. Test unauthorized original access. Label sanitized/re-encoded image bytes separately from uploaded-source originals, and pin an authorized export inventory/revision across edits/deletions. Embed and direct CDN protection are distinct; protect the direct paths actually used. Retain existing managed delivery rather than streaming large libraries through the application or constructing ZIPs in browser memory. Background exports need bounded workers, streaming output, progress/retry/cancel, authorized expiring downloads and cleanup. Exclude other users' private data and raw identity records.

Unpublish/hide stops discovery and new sales; it is different from retirement/deletion. Existing purchased access must follow an explicit accepted policy rather than an accidental code-side revocation. Safety removals must stop unsafe authorization promptly. Deletion should track originals, renditions, previews, thumbnails, captions, caches and replay assets, with honest bounded token/cache lifetimes and legally required holds. Copies already downloaded or independently replicated cannot be recalled.

This improves trust, portability and operational clarity; it does not by itself establish a legal exemption or eliminate platform obligations. Current Bunny AUP permits lawful adult content conditionally and places content responsibility on its client; live use has additional approval language. Livepeer Studio terms do not provide blanket acceptance for this exact adult use. Keep unapproved adult live disabled and obtain documented exact-use acceptance. Wallet custody, media storage control, copyright, performer consent and platform liability must be described separately.

### AUTH-06 — P1/P2 — Fast or out-of-order webhooks can be permanently lost before session persistence

### AUTH-09 — P1/P2 — Public avatar storage bypasses the existing image safety boundary

### AUTH-10 — P1/P2 — Many admin and profile mutations check an Idempotency-Key but never enforce it

## Two precise refinements to add to the handoff

1. **Separate original retention from original exposure.** The current Bunny API documents `KeepOriginalFiles`, `ExposeOriginals`, and `AllowEarlyPlay` separately. Exposed originals are not DRM protected, and enabling Early-Play also enables exposure. Retention for creator portability must not accidentally enable publicly accessible originals. Require an explicit library setting/proof check, private/authorized original access, and tests that ordinary/public users cannot obtain original files. This is a proposed configuration hardening requirement; no live Bunny configuration was available to inspect, so it is not a confirmed live exposure.
2. **Label exported bytes accurately.** `apps/api/src/modules/content/image-sanitizer.ts:49-51,66-71,100-106` rotates and re-encodes images, strips metadata and emits a new retained byte stream. That is a sanitized retained asset, not necessarily the byte-for-byte uploaded source original. The export manifest should label source original, sanitized retained original, and rendition distinctly, with hashes for the actual bytes exported. Do not undo image safety/privacy handling merely to advertise original retention. If source-byte preservation is desired, propose its security, retention and cost policy explicitly first.

Useful export acceptance detail: pin a consistent authorized inventory/revision for a job; handle edit/delete/retire races; recheck export/download authorization and relevant account/safety policy; avoid a long-lived export link becoming a second access authority. These are implementation guidance, not new reproduced defects.
